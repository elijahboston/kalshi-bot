# Tail-market entry gate (2026-05-29)

**Status:** Accepted
**Date:** 2026-05-29
**Deciders:** Elijah Boston

## Why

Tail markets (`upper_tail` / `lower_tail`) were [unblocked on 2026-05-05](./post-sharpening-regression.md) to let the estimator score them, and on [2026-05-26](./execution-unblock-2026-05-26.md) `minContractPrice` was bypassed for high-confidence signals — including tails. Two weeks later the empirical results are bad:

| Cohort | Trades | Win rate | PnL |
|---|---|---|---|
| Bracket markets (last 30d) | 149 | 33.6% | −$49.42 |
| **Tail markets (last 30d)** | **9** | **11.1%** | **−$38.36** |

Concretely, the resolved tail tape:

```
KXHIGHAUS T70  NO @50¢  → YES (lost $5)
KXHIGHAUS T81  NO @50¢  → YES (lost $5)
KXHIGHDEN T71  NO @20¢  → YES (lost $5)
KXHIGHLAX T69  NO @50¢  → YES (lost $5)
KXHIGHMIA T85  NO @62¢  → NO  (won  $4.56)
KXHIGHNY  T62  NO @50¢  → YES (lost $5)
KXHIGHNY  T66  YES @25¢ → NO  (lost $5)
KXHIGHNY  T66  YES @25¢ → NO  (lost $5)
KXHIGHNY  T76  NO @33¢  → YES (lost $7.92)
```

Every loss was a mid-priced tail bet (20–50¢ entry). The one winner was a deep-ITM NO at 62¢ — the only entry where being wrong was capped at a small per-contract loss.

The estimator's tail probability is not reliable enough to justify mid-priced positions. Until we improve it, we should only take tails as cheap "deep tail" bets — small per-contract downside, model only needs to be right occasionally.

## Change 1 — New `evaluateTailGate` helper

[`app/signals/services/entry-gates.ts`](../../app/signals/services/entry-gates.ts) — pure function called from the orchestrator's Phase 3 decision block.

```ts
export function evaluateTailGate(input: TailGateInput): TailGateResult {
  const { market, side, marketPrice, tailMaxEntryPrice } = input;
  const isTail =
    market.marketType === "upper_tail" || market.marketType === "lower_tail";
  if (!isTail) return { allowed: true };
  if (tailMaxEntryPrice <= 0) return { allowed: true };

  const entryPrice = side === "yes" ? marketPrice : 1 - marketPrice;
  if (entryPrice > tailMaxEntryPrice) {
    return { allowed: false, reason: `tail entry ${entryPrice*100}¢ > max ${tailMaxEntryPrice*100}¢` };
  }
  return { allowed: true };
}
```

Bracket markets pass through unchanged. The gate is a pure helper so it's unit-testable independently of orchestrator state.

### Initial runtime value

```sql
INSERT INTO runtime_config(key, value, updated_at)
VALUES ('tail_max_entry_price', '0.10', strftime('%Y-%m-%dT%H:%M:%fZ','now'))
ON CONFLICT(key) DO UPDATE SET value = excluded.value, updated_at = excluded.updated_at;
```

10¢ is intentionally tight. Of the 10 tail trades in the audit, zero would have passed at this cap. That sounds harsh, but the data says current tail entries are not edge — they're a different bet type the model isn't qualified to take. Better to take few or none than continue bleeding.

## Wire into orchestrator

[`app/engine/services/orchestrator.ts`](../../app/engine/services/orchestrator.ts) — new `else if (!tailGate.allowed)` clause in the Phase 3 decision ladder, evaluated after `edge`, `confidence`, and sniper-window checks pass. When the gate trips, the signal is recorded with `skipReason` set to e.g. `"tail entry 50¢ > max 10¢"` so it's queryable via the `signals` table.

The gate is computed unconditionally each tick (cheap pure function) so its absence doesn't subtly change non-tail behavior.

## Expected impact

- All current mid-priced tail bets stop firing (10/10 of the audit-window tails would have been blocked at 10¢).
- Deep-cheap tail bets (≤10¢) still allowed — the model's confidence on rare events combined with capped per-contract downside is the right shape for tails.
- −$38 / 30d run-rate of tail bleed → 0.

## Tests

[`app/signals/services/entry-gates.test.ts`](../../app/signals/services/entry-gates.test.ts) — 7 tests:

- Non-tail markets pass unconditionally
- `tailMaxEntryPrice = 0` disables the gate
- NO side: blocked when `1 − marketPrice > cap`
- NO side: allowed on strong-YES markets (cheap NO)
- YES side: blocked when `marketPrice > cap`
- YES side: allowed on long-shot tails (cheap YES)
- Equality at the cap is allowed

## Verification (target ~2026-06-05)

- `SELECT COUNT(*) FROM signals WHERE skip_reason LIKE 'tail entry%' AND created_at > date('now','-7 days')` — should be non-zero, confirming the gate fires.
- `SELECT COUNT(*) FROM trades t JOIN markets m ON t.ticker = m.ticker WHERE m.market_type IN ('upper_tail','lower_tail') AND t.filled_at > date('now','-7 days')` — should approach 0, or only deep-cheap entries.
- Net PnL from tail markets (per the audit query in the doc) should be flat-to-positive over the week.

## What this still doesn't fix

- The estimator itself is still bad at tails. The right long-term fix is to compute tail probabilities differently — e.g., using the full ensemble distribution's tail mass with explicit fat-tail treatment, rather than the current normal CDF.
- If the gate stops the bleed, we may want to *relax* `tailMaxEntryPrice` over time. Plan revisit at 0.15 then 0.20 once two consecutive weeks of green tail PnL accumulate.
